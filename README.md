**사진 분류를 기기 안에서, 모델은 갈아 끼울 수 있게.** 서버에 사진을 올리지 않고 휴대폰에서
직접 추론합니다. 분류 모델은 앱에 고정하지 않고 실행 중에 목록을 받아 고르고 내려받습니다.

Flutter · TensorFlow Lite · MobileNetV2 (ImageNet 1000 클래스)

> **iPhone 17 Pro Max 실측: 한 장 11~13 ms (추론 약 9 ms).**
> 처음엔 41~52 ms였고 77~81%가 모델이 아니라 **사진을 텐서로 만드는 전처리**였습니다. 플랫폼 디코더로
> 바꿔 3.6~4.2배 줄였고, 기기에서 ImageNet 1000장으로 정확도가 떨어지지 않았음을 확인했습니다
> (86.0% → 86.4%, p = 0.69).
> 입력 정규화 기본값이 틀려 있던 결함을 찾아 고쳤습니다 (ImageNet 1000장, 같은 전처리에서 top-1 75.0% → 83.9%).

---

## 왜 온디바이스인가

사진 분류를 서버로 보내면 세 가지 비용이 생깁니다. 사용자 사진이 외부 네트워크에 노출되고,
오프라인에서 사용하는데 한계가 발생하고, 사진의 수만큼 추론 비용이 발생합니다. 
갤러리 정리처럼 **사진 수천 장을한 번에 훑는 작업**에서는 이 세 가지가 다 증가하게 됩니다.

그래서 추론을 온디바이스로 진행하도록 했습니다. 
다만 모델을 앱 번들에 넣으면 앱 용량이 커지고 모델을 바꿀 때마다 스토어 심사를 다시 받아야하는 문제가 발생했습니다
빠라서 . **모델만 서버에 올리고 따로 다운받는 구조**로
그 둘을 분리했습니다.

## 구조

```
앱 시작
  │
  ├── GET /models                     서버에서 사용 가능한 모델 목록
  │
  ├── 사용자가 모델 선택
  │     └── GET /download-model?model_name=...   (zip)
  │           └── 압축 해제 → <앱문서>/models/<모델명>/{model.tflite, labels.txt}
  │                 └── 선택 상태를 shared_preferences에 저장
  │
  └── 사진 선택 (image_picker, 네이티브에서 긴 변 1024px로 축소)
        └── 네이티브 디코드하며 224×224로 축소 → [-1,1] 정규화 → NHWC float32
              └── TFLite Interpreter.run()  ← 기기 내 추론
                    └── 상위 3개 클래스 + 확률
```

| 파일 | 역할 |
|---|---|
| `lib/services/image_classifier.dart` | TFLite 인터프리터 로드, 전처리, 추론, 상위 3개 추출 |
| `lib/api/api_service.dart` | 모델 목록 조회, zip 다운로드·해제, 모델별 폴더 관리 |
| `lib/screens/home_screen.dart` | 모델 선택 UI, 사진 선택, 결과 표시 |

모델은 앱 문서 디렉토리에 **모델명 폴더**로 나뉘어 저장되므로 여러 모델을 받아두고
바꿔 쓸 수 있습니다.

## 실행

모델 서버와 앱 두 개를 실행 시킵니다. 휴대폰과 서버가 **같은 와이파이**에 연결 되어 있으면 됩니다.

```bash
# 1) 모델 받기 + 서버 (맥, 표준 라이브러리만 사용)
python3 tools/fetch_model.py        # tools/models/mobilenetv2/{model.tflite,labels.txt}, SHA-256 확인
python3 tools/model_server.py       # 0.0.0.0:9000 — 앱 빌드 명령을 주소까지 채워 출력합니다

# 2) 앱 (폰 연결)
flutter pub get
flutter run --profile --dart-define=MODEL_SERVER=http://<맥 IP>:9000
```


**모델.** TensorFlow 공식 [tflite-support](https://github.com/tensorflow/tflite-support)
테스트 데이터의 `mobilenet_v2_1.0_224.tflite`로 고정했습니다 (float32, 1001 클래스,
14.0MB, SHA-256 `ff5cb7f9…`). 첫 커밋의 `labels.txt`가 이 모델의 내장 라벨과 1001줄
모두 같아서, 원래 쓰던 모델도 같은 계열이었을 가능성이 높습니다.

(권한: iOS는 `ios/Runner/Info.plist`에 사진 접근·로컬 네트워크 권한이, Android는
`permission_handler`로 런타임 요청과 매니페스트의 `INTERNET`·평문 HTTP 허용이 들어가
있습니다.)

## 측정

앱 우상단 **속도계 아이콘**을 누르면 선택한 사진으로 50여 회 추론해 구간별
**중앙값**을 표로 보여줍니다. **`--profile`이나 `--release` 빌드에서 재야 합니다.**

(예: `decode 17.7ms | resize 13.0ms | tensor 1.1ms | infer 9.5ms | post 0.2ms | total 41.5ms`).

**iPhone 17 Pro Max · `flutter run --profile` · 정규화 `[-1,1]`**
전처리: 피커가 긴 변 1024px로 리사이징 → `image` 패키지 디코딩(순수 Dart) → 224×224 로 리사이징.
사진마다 추론 20회의 중앙값(워밍업 3회 제외), 단위 ms.
원본 캡처: [`docs/measurements/2026-09-15-iphone17promax/`](docs/measurements/2026-09-15-iphone17promax/)

| 구간 | 커피잔 650×650 | 고양이 1000×667 | 키보드 1320×701 → 1024×544 |
|---|---:|---:|---:|
| 디코드 | 17.7 | 24.1 | 19.5 |
| 리사이즈 (→224×224, 면적 평균) | 13.0 | 16.5 | 15.6 |
| 텐서 변환 | 1.1 | 1.1 | 1.1 |
| **추론** | **9.5** | **9.8** | **9.6** |
| 후처리 | 0.2 | 0.2 | 0.2 |
| **전체** | **41.5** | **51.7** | **46.0** |
| 전처리 비중 | 77% | 81% | 79% |


추론 최적화보다 시급했던 전처리 병목 해소

모델 추론 시간은 약 10 ms로 이미 충분히 최적화되어 있었습니다. 여기서 모델을 추가 양자화해 추론 지연시간을 절반으로 줄여봤자 전체 파이프라인 기준 개선율은 10% 안팎에 그칩니다.

진짜 병목은 31~41 ms를 점유하던 이미지 디코딩과 리사이징이었습니다. 1024px 이하 이미지임에도 Dart 계층의 디코딩에 18~24 ms, 면적 평균 축소에 13~17 ms가 소모되었습니다. 면적 평균 리사이징은 픽셀 집계를 거치므로 Nearest 대비 연산 비용이 크지만, 모델 인식 정확도를 유지하려면 타협할 수 없는 전처리였습니다.

따라서 전체 원본을 메모리에 올린 뒤 리사이즈하는 비효율을 제거하고자, **네이티브 레벨에서 디코딩과 224×224 다운샘플링을 단일 패스로 처리하는 경로(ImageDecoder.platform)**를 도입해 동일 입력 환경에서 지연시간을 비교 검증했습니다.

### 디코더 비교 — 속도 3.6~4.2배, 정확도 차이 없음 → `platform`을 기본값으로

전처리 14배 단축과 보간 필터 불일치 문제 해결

캐시 간섭을 배제하기 위해 동일 기기·동일 빌드에서 두 디코더를 번갈아 20회 교차 측정하고 중앙값을 산출했습니다. 네이티브 플랫폼 경로는 「디코드+다운샘플링」과 「픽셀 버퍼 읽기」 단계로 나누어 프로파일링했습니다.

그 결과, **전처리 시간은 31~40 ms에서 2.2~2.8 ms로 급감(약 13~15배 단축)**했습니다. 전체 파이프라인 처리량 역시 3.6~4.2배 증가해 초당 80~90장을 처리하는 수준에 도달했습니다. 이제 병목은 전처리가 아니라 **전체 지연시간의 75~80%를 차지하는 모델 추론(9 ms)**으로 넘어왔고, 비로소 모델 양자화가 전체 속도에 유의미한 영향을 미치는 단계에 진입했습니다.

다만 예상치 못한 정밀도 편차가 있었습니다. 두 경로 모두 Top-1 예측 클래스는 일치했으나, 소프트맥스 신뢰도 점수가 8~11%p가량 요동쳤습니다(커피잔과 키보드는 하락, 고양이는 상승). 플랫폼 디코더가 내부적으로 사용하는 리샘플링 필터가 Dart의 면적 평균과 다르기 때문이었습니다. 데스크톱 환경의 Pillow와 OpenCV에서 다양한 보간 필터(Bilinear, Bicubic, Lanczos, Box 등)를 시도해보았지만, 기기 고유의 네이티브 다운샘플링 수치와 완벽히 맞아떨어지는 필터는 없었습니다.

결국 PC 시뮬레이션으로 정확도를 근사하는 방식은 한계가 있다고 판단해, 기기 위에서 레이블 데이터를 직접 태워 검증하는 구조로 전환했습니다. 테스트 셋(ImageNet 1,000장 표본)을 기기로 내려보내 두 경로의 추론 정합성을 직접 비교 측정했습니다.

| 사진 (입력 크기) | 디코더 | 디코드(+축소) | 리사이즈 / 픽셀 읽기 | 텐서 | 추론 | **전체** | 상위 1개 |
|---|---|---:|---:|---:|---:|---:|---|
| 커피잔 650×650 | dartImage | 17.4 | 12.6 | 1.1 | 9.3 | **40.7** | cup 80.5% |
| | platform | 1.6 | 0.5 | 0.1 | 9.0 | **11.3** | cup 72.5% |
| 고양이 1000×667 | dartImage | 23.3 | 16.0 | 1.1 | 9.0 | **49.6** | Persian cat 57.4% |
| | platform | 1.8 | 0.8 | 0.1 | 8.9 | **11.8** | Persian cat 68.7% |
| 키보드 1024×544 | dartImage | 18.5 | 14.3 | 2.4 | 9.4 | **44.7** | computer keyboard 48.9% |
| | platform | 2.2 | 0.5 | 0.1 | 9.5 | **12.5** | computer keyboard 39.1% |

**기기 정확도 (iPhone 17 Pro Max, profile, 정규화 `[-1,1]`, 1000장 실패 0)**

| 디코더 | top-1 | top-5 | 한 장 전체 중앙값 |
|---|---:|---:|---:|
| dartImage (Dart 디코드 + 면적 평균) | 86.0% | 97.7% | 29.5 ms |
| **platform** (네이티브 디코드+축소) | **86.4%** | **98.1%** | **11.2 ms** |

- 짝지어 보면 dartImage만 맞힌 사진 27장, platform만 맞힌 사진 31장입니다. 차이 +0.4%p,
  95% 신뢰구간 −1.1~+1.9%p, 정확 McNemar p = 0.69. **차이가 없다고 말할 수 있는 범위는 ±2%p
  정도까지**이고, 그보다 작은 차이는 1000장으로 구분할 수 없습니다. 상위 1개는 920장(92.0%)에서 같았습니다.
- **평가 배관 검증:** 기기의 dartImage 86.0%는 PC에서 같은 전처리(PIL `BOX`)로 잰 86.0%와
  정확히 같습니다. 앱의 평가 코드와 PC 스크립트가 같은 것을 재고 있다는 뜻입니다.
- 이 표본의 사진은 긴 변 500px 안팎이라 224px까지 2배 남짓만 줄입니다. 한 장 시간(29.5 ms)이 위
  사진 3장(40~50 ms)보다 짧은 것도 그래서입니다. **피커를 거친 1024px 사진(4.6배 축소)에서 두 필터의
  차이는 따로 재지 않았습니다.**

→ 정확도를 잃지 않고 2.6~4.2배 빨라지므로 **기본 디코더를 `platform`으로 바꿨습니다.** 이제 한 장
시간의 약 80%가 추론이라, 다음으로 줄일 곳은 모델(INT8 양자화)입니다.

같은 창에서 먼저 잰 dartImage 전체는 35.8 / 43.4 / 39.8 ms로, 추론 80여 회 뒤에 잰 위 표보다
5~6 ms 빨랐습니다. 순서·발열 영향으로 봅니다. 사진 3장·기기 1대 기준이라 배수는 대략값으로만
인용합니다.

전처리와 추론을 따로 재는 이유는, 온디바이스에서 **전처리가 추론보다 오래 걸리는
경우가 흔하기** 때문입니다. 추론 시간만 보고하면 절반만 보는 셈입니다.

### 전처리: 중첩 List → Float32List

처음 구현은 224×224×3 픽셀을 Dart 중첩 `List`에 한 픽셀씩 채웠습니다
(`List.generate` 4중첩 + 이중 루프 = 15만 회 대입). 이걸 `Float32List` 연속 쓰기로
바꿨는데, 여기에 한 단계가 더 있었습니다.

`Tensor.setTo()`에 `Float32List`를 그대로 넘기면 빨라지지 않습니다.
tflite_flutter의 `ByteConversionUtils.convertObjectToBytes`는 `Uint8List`와
`ByteBuffer`만 그대로 통과시키고, 그 밖의 `List`는 **원소마다 4바이트 버퍼를 새로
만들어** growable `List<int>`에 `addAll` 합니다. 즉 15만 번의 할당이 그대로 남습니다.
같은 메모리를 가리키는 `Uint8List` 뷰로 넘겨야 변환 없이 memcpy 한 번으로 끝납니다.

```dart
inputTensor.setTo(buffer.buffer.asUint8List());  // 뷰 — 복사 없음
```

두 경로를 다 남겨 뒀기 때문에 같은 기기에서 전/후를 비교할 수 있습니다
(`ImageClassifier.useFastPreprocess`, 속도계 버튼이 둘 다 측정).

| 텐서 변환 방식 | 커피잔 | 고양이 | 키보드 |
|---|---:|---:|---:|
| 중첩 List (기존) | 3.1 ms | 3.5 ms | 3.6 ms |
| Float32List + Uint8List 뷰 | 1.2 ms | 1.2 ms | 2.7 ms* |

2.6~3.0배 빨라졌지만 **줄어든 시간은 2 ms 남짓, 전체의 5% 정도입니다.** 할당 15만 회를 없앤
것 자체는 맞는 수정이지만, 이 앱의 병목은 아니었습니다. \*키보드의 2.7 ms는 같은 경로를 잰
위 표(1.1 ms)와 어긋나는 튀는 값입니다. 비교 측정이 앞 측정 직후 연달아 돌아 발열이나 GC가
섞였을 수 있어, 배수로 인용하지 않습니다.

### 정규화 범위 확인 — `[-1,1]`로 확정

MobileNetV2 배포본은 입력을 `[0,1]`로 기대하는 것과 `[-1,1]`로 기대하는 것이 섞여
있습니다. **틀려도 에러가 나지 않고 정확도만 조용히 떨어집니다.** 이 모델은 `[-1,1]`입니다.

1. **메타데이터.** 모델에 박힌 `NormalizationOptions`가 mean 127.5 / std 127.5
2. **정확도.** ImageNet 클래스당 1장, 1000장을 앱과 같은 전처리(크롭 없이 전체 리사이즈)로
   분류했습니다 ([`tools/check_normalization.py`](tools/check_normalization.py),
   결과 [`tools/results/normalization.json`](tools/results/normalization.json))

| 리사이즈 | 정규화 | top-1 | top-5 |
|---|---|---:|---:|
| nearest (이전 앱) | `[0,1]` | 75.0% | 92.8% |
| nearest (이전 앱) | **`[-1,1]`** | **83.9%** | **96.8%** |
| bilinear | `[0,1]` | 75.4% | 92.4% |
| bilinear | **`[-1,1]`** | **85.8%** | **97.8%** |

같은 사진 1000장을 짝지어 비교하면 `[-1,1]`만 맞힌 사진이 109장, `[0,1]`만 맞힌 사진이
20장입니다 (정확 McNemar p ≈ 5×10⁻¹⁶). 사진이 학습 세트에 들어 있을 수 있어 절대
정확도는 낙관적이고, 두 정규화의 **차이**만 의미가 있습니다.

**기기에서도 같은 현상이 나왔습니다.** 고양이 사진은 틀린 `[0,1]`이 같은 답(Persian cat)을
**더 높은 확률**(74.8% vs 57.4%)로 냈고, 키보드 사진은 `[0,1]`에서 답이 modem(10.5%)으로
바뀌었습니다(`[-1,1]`은 computer keyboard 48.9%).

**PC 재현.** 같은 사진을 앱과 같은 전처리(1024px 축소 → 224 면적 평균, PIL `BOX`)로 PC에서
돌리면 상위 1개가 여섯 경우(사진 3장 × 정규화 2개) 모두 기기와 같았고 — 키보드의 modem까지 —
확률 차이는 0.4~5.7%p였습니다. 기기의 Dart 전처리가 의도대로 동작한다는 확인입니다.
nearest로 돌리면 `[0,1]` 키보드가 computer keyboard로 나와 기기와 달랐습니다.

**처음 계획은 틀렸습니다.** 속도계 버튼에서 사진 한 장을 두 범위로 분류해 "확률이 뚜렷하게
높은 쪽"을 고르려 했는데, 틀린 정규화도 쉬운 사진은 대개 맞히고 확률이 더 높게 나오기도
합니다. 1000장에서 이 방법이 맞는 쪽을 고른 비율은 **65%**였습니다. 그래서 결정은 위의
두 근거로 하고, 버튼의 비교 표는 기기에서 두 경로가 모두 동작하는지 보는 확인용으로만
남겼습니다.

### 리사이즈 보간 — 폰 사진에서는 nearest가 크게 틀린다

위 1000장은 긴 변 500px 안팎이라 224px까지 2배 남짓만 줄입니다. 그래서 nearest와
bilinear 차이가 1.9%p에 그쳤습니다(면적 평균은 86.0%). 아이폰에서 실제로 돌려 보니 분류가 눈에 띄게 틀렸습니다.
원본이 4032×3024라 18배를 줄이는데, nearest는 18칸마다 한 픽셀만 집기 때문입니다.

긴 변 3000px 이상 사진 45장(Wikimedia Commons에서 ImageNet 클래스명으로 검색)으로 짝지어
비교했습니다. 정규화는 `[-1,1]`입니다.

| 전처리 | top-1 | top-5 |
|---|---:|---:|
| 원본 → 224 nearest (이전 앱) | 10/45 | 23/45 |
| 원본 → 224 면적 평균 | 19/45 | 27/45 |
| 1024px로 축소 → 224 면적 평균 (**현재 앱**) | **19/45** | **28/45** |
| 1024px로 축소 → 중앙 크롭 → 224 bilinear | 16/45 | 27/45 |

현재 방식만 맞힌 사진은 10장, 이전 방식만 맞힌 사진은 1장입니다 (정확 McNemar p ≈ 0.012).
이전 방식의 오답은 `chain mail`, `honeycomb`, `window screen`, `knot`처럼 모아레 질감
클래스가 많았습니다. 검색 결과에 사진이 딸려 온 것이라 라벨에 잡음이 있어 절대 정확도는
의미가 없고, 같은 사진끼리 비교한 **차이**만 봅니다. 중앙 크롭은 정확도를 올리지 못했고
피사체를 자를 수 있어 쓰지 않습니다. 1024px 축소는 정확도는 그대로 두고 12MP JPEG를 Dart로
디코드하는 비용을 없앱니다.

## 남겨진 과제 / 다음 스프린트 목표

- 추론이 전체 시간의 80%를 차지하는 새 병목이 되었습니다. INT8 양자화 모델을 도입해 모델 크기 절감, 속도 개선, 정확도 보존율을 기기 위 1,000장 벤치마크로 다시 한 번 검증할 계획입니다.

- 양자화 적용 전, 텐서 타입 분기 구조를 먼저 고쳐야 합니다. 현재 네이티브 플랫폼 디코더를 타는 고속 경로는 float32 전용으로 작성되어 있어, INT8 모델을 물리면 곧바로 기존의 느린 Dart 경로로 폴백됩니다. 타입 추상화 정리가 선행되어야 공정한 비교가 가능합니다.

- 필터 왜곡이 극대화되는 4.6배 축소 환경은 아직 확인하지 못했습니다. 1,000장 샘플은 원본 크기가 작아 2배 축소에 불과했기 때문에 보간 알고리즘별 차이가 희석되었을 가능성이 큽니다. 1024px 원본 표본을 확보해 다시 측정해야 합니다.

- 12MP 카메라 원본과 EXIF 회전 검증이 빠져 있습니다. 갤러리 정리 기능의 실제 입력은 12MP급 HEIC/JPEG입니다. 시스템 피커가 자체적으로 사진을 줄이는 시간은 현재 프로파일러에 잡히지 않으므로 따로 분리해 재야 합니다. 또한 순수 JPEG 디코더와 달리, 네이티브 플랫폼 경로와 HEIC 포맷에서도 세로 사진의 EXIF 방향 메타데이터가 정상 반영되는지 실기기 확인이 필요합니다.

- ImageNet-1K 레이블 셋의 본질적 한계가 존재합니다. 전처리가 아무리 완벽해도 인물, 풍경, 캡처된 문서처럼 1,000개 클래스에 속하지 않는 일상 사진들은 엉뚱한 클래스로 분류됩니다.

- 모델 다운로드의 안전장치가 부실합니다. 네트워크가 끊기면 빈 목록만 뱉고 로그를 남기는 수준에 그쳐 재시도 루프와 사용자 안내가 시급합니다. 또한 파이썬 도구와 달리 앱 단에서는 내려받은 zip 파일의 SHA-256 해시를 검증하지 않고 풀어버립니다. API 응답에 체크섬을 실어 무결성을 확인하도록 보완해야 합니다.

- 메인 UI 스레드가 추론 연산을 떠안고 있습니다. 수천 장의 사진을 연속으로 스캔하는 실제 시나리오에서는 화면이 프리징될 수밖에 없으므로, 워커 분리(IsolateInterpreter)를 통해 UI와 추론 스레드를 즉시 격리해야 합니다.
